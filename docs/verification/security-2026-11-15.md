# Labeeb security review — 2026-11-15

Target: local working tree, version 0.1.47, Windows. This is a source review and targeted regression verification, not a penetration-test certification. Existing unrelated work was preserved. Fixes are in source; existing EXE/MSIX artifacts have not been rebuilt or published by this review.

## Confirmed findings and fixes

### SEC-01 — Download accelerator discloses the full referring page URL (Medium)

The Windows download callback copied the current tab URL into `accelerator::Source.referer`. `accelerator::request` sent it unconditionally as the HTTP Referer, including to a different origin. A download destination could therefore receive private paths, query parameters and fragments, regardless of the page's referrer policy. The impact depends on whether the referring URL contains sensitive information; no real credential was used or extracted during this review.

Fix: remove page-referrer capture and transmission. Disable automatic accelerator redirects and automatic referrer generation. Redirected downloads remain with WebView2, which owns browser cookie/referrer policy. This also avoids forwarding manually captured cookies through native HTTP redirect handling. Downloads requiring a Referer may remain on the ordinary engine path instead of accelerating.

Evidence: source review of `src-tauri/src/desktop.rs` and `src-tauri/src/accelerator.rs`. Regression `accelerator::tests::redirects_do_not_replay_browser_credentials` runs a local HTTP server, checks a synthetic session cookie on the initial request, verifies absence of Referer, returns a same-origin redirect and verifies that no second connection occurs and the accelerator declines the download.

### SEC-02 — Custom downloaded files lack Windows Internet-zone provenance (Medium)

Accelerated downloads write a new `.labeeb-part` file, cancel the WebView2 download, remove its destination and rename the custom file into place. The custom file did not receive `Zone.Identifier`; any zone metadata on the discarded engine file is not transferred by this operation. The separate direct-download writer also did not mark its output. Consequently, applications relying on Internet-zone provenance may not apply their usual downloaded-file protections. Opening a downloaded executable still requires user action; this is not automatic code execution.

Fix: add `download_security::mark_internet`, writing `[ZoneTransfer]` / `ZoneId=3` on Windows before a custom download is reported successful. Mark the accelerated partial file before its final rename. Fail the custom transfer if marking fails; do not silently report an unmarked file as complete. No private source URLs are stored in the marker. Filesystems without ADS support can therefore reject these custom transfers. Other platforms remain unchanged; macOS quarantine was not implemented or tested in this Windows review.

Evidence: the previous custom writers and finalization path contain no zone-marking operation. Windows regression `download_security::tests::internet_zone_survives_final_rename` confirms the alternate stream survives the final rename and file content is unchanged. A live SmartScreen/UI exploit was not performed.

Microsoft's stream format: https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/6e3f7352-d11c-4d76-8c39-2516a9df36e8

### Dependency advisories — patched versions selected

The initial RustSec run reported five known advisories: `RUSTSEC-2026-0459` in bundled `libsqlite3-sys 0.36.0`, and `RUSTSEC-2026-0367`, `0368`, `0369`, `0429` in `zip 2.6.1`.

- SQLite: the advisory requires opening a crafted database together with a mismatched sibling WAL file, potentially returning uninitialized page-cache memory. No remote web-page path to replacing Labeeb's database/WAL was established. Updated `rusqlite` to 0.41.1 and its bundled SQLite binding to `libsqlite3-sys 0.39.1`.
- ZIP: the advisories concern general extraction APIs and symlink/Unix-permission handling. Labeeb reads a selected entry from a hash-pinned tools archive into a fixed filename; it does not call `ZipArchive::extract` or the stream extraction API. Updated `zip` to 9.5.1 anyway, and adapted entry-name validation to its fallible API.
- The post-update RustSec run reports **zero vulnerability entries**. Five informational warnings remain: four unmaintained crates (`proc-macro-error`, `zbus_names`, `zvariant`, `zvariant_derive`) and an unsoundness warning for `glib`. Windows-target dependency-tree inspection of `glib`, `proc-macro-error` and `zvariant` produces no dependency paths; these warnings relate to other platform dependencies and must be revisited for a Linux build. They are not silently suppressed.
- Both before/after JSON audit results are preserved alongside this report. These are dependency matches, not five demonstrated exploits in Labeeb.

## Reviewed boundaries

- Packaged main webview capability and native caller checks; remote tabs have distinct labels. No direct remote-page-to-privileged-command path was established during review.
- API keys retrieved from OS keyring by native code; provider requests disable redirects. No key was printed or sent to a test server.
- Assistant Markdown suppresses HTML and remote images; actionable links require HTTP(S), no credentials, and an explicit user click. The assistant has no action tools.
- Explicit page-context requests, bounded extraction, exclusion of form inputs, navigation-race checks, and treatment of page text as untrusted. Prompt-injection resistance is not guaranteed by these measures.
- Direct downloader public-address checks, pinned resolution, no proxy/redirects, size bounds, generated filenames and cleanup.
- Password origin checks, vault persistence tests, Viora file/collection allowlists and storage-token checks, diagnostics URL redaction, media-tool argument handling and pinned tool-download hashes.

## Limits and remaining verification

No real-user secrets, authenticated websites, production accounts or destructive payloads were used. This review did not exercise hostile remote-frame IPC in the installed application, audit WebView2/WKWebView internals, fuzz all parsers, test macOS, inspect every bundled Viora dependency or certify Store packaging/signatures. Local browsing/chat databases are local storage, not a guarantee of encryption against another process running as the same OS user. The failed automated scan should be rerun in a working Codex Security environment before treating its coverage as complete.
